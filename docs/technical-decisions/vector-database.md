# Vector Database Decision

**Status: Accepted design; retrieval implementation pending.** Use pgvector in PostgreSQL for document embeddings and chunks. The vector service runs and initializes the extension only when Docker can start; no table, index, or query exists yet.

## Comparison

- **pgvector:** embeddings and metadata filtering share PostgreSQL SQL, one database technology, and transactional behavior. A good MVP fit for local deployment and moderate vector collections. Index behavior and recall/latency require measurement.
- **Qdrant:** purpose-built vector search with rich filtering and operational APIs; can be preferable when vector workloads dominate and a separate service is acceptable.
- **Milvus:** designed for large-scale distributed vector search and varied index options; better when data volume and throughput justify its operational footprint.
- **ChromaDB:** quick local experimentation and prototyping; convenient API, but less attractive as the authoritative production database with relational metadata needs.
- **FAISS:** fast similarity-search library, not a server/database by itself. Useful embedded in a process or for offline experiments, but persistence, metadata filtering, and multi-user isolation must be built around it.

## Planned retrieval behavior

Store each chunk's vector with document ID, owner ID, chunk index, and source metadata. Query vectors are generated by the same embedding model/version. Filter by verified owner and selected documents, then rank by the chosen distance metric. Similarity is candidate relevance, not truth. Evaluate top-k and thresholds against real Hindi and English questions.

## Limitations and migration

Vector index speed and recall trade-offs depend on corpus size and index tuning. Model changes require re-embedding documents. Move to Qdrant or Milvus if measured vector scale, throughput, or specialized filtering exceeds the single PostgreSQL service. Keep the application retriever behind a service interface to ease migration.
